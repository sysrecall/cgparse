# AI usage disclosure

Two distinct things are disclosed here:

1. **Development-time AI assistance** — how this repository was built.
2. **Runtime AI** — the models the product itself calls, with the exact prompts.

---

## 1. Development-time AI assistance

### Tooling

The codebase was written with an **AI coding agent (OpenCode)** operating on the
local repository, with a large language model as the reasoning backend. The human
author set the requirements, made every architecture decision and reviewed the
result at each step; the agent produced code, migrations, tests, scripts and docs,
and ran the test/lint/evaluation commands.

The agent ran locally against the repository; the code context it read was sent to
the model provider as part of each request. `.env` was never read wholesale — the
single inspection of it redacted the credentials — and secrets exist only in that
untracked file.

### Division of responsibility

| Decided by the human (not AI) | Produced by the agent |
|---|---|
| Stack and provider choices (Supabase, Tigris, Upstash, OpenParser, NVIDIA NIM) | Project scaffolding, dependency wiring |
| Storage/queue/DB topology; UUID PKs, string statuses + `CHECK`s, `NUMERIC(12,2)` money | SQLAlchemy models, hand-written initial migration |
| Pipeline stage boundaries and queue split (`ocr` / `llm`) | Celery chain, stage implementations |
| Extraction policy: heuristics first, heuristics win, unknown stays `null`/`0.0` | Regex heuristics, LLM merge, Pydantic contract |
| The six validation rules and their severities | Rule implementations and `needs_review` routing |
| Search behaviour (FTS + hybrid semantic ranking) | FTS queries, vector query, RRF fusion, filters, grouping |
| Correction semantics (human values `confidence=1.0`, `source="human"`, survive reprocess) | Endpoints and re-validation flow |
| UI pages, styling rules (`STYLE_GUIDE.md`) | Next.js components, polling, SWR wiring |
| Testing/evaluation strategy and the dedicated dev DB | Suites, corpus generator, harness, report |

Every step ended with an explicit approval checkpoint; ambiguous points were
raised as questions instead of being guessed.

### How AI output was verified

- **155 automated tests** pass (30 app-core, 72 processing, 53 api), including
  DB-marked integration tests against a dedicated Supabase dev project.
- **`ruff` clean** in all three Python projects and `scripts/`.
- **Real-provider evaluation** over a 31-document labeled corpus — actual OCR and
  LLM calls, not mocks — producing `docs/metrics_report.md` / `docs/metrics.json`.
- **Diff review per step**, with semantically scoped commits so each change is
  auditable in isolation.
- Bugs the tests caught in AI-written code (and fixed) are visible in history:
  XLSX empty cells read as `"nan"`, comma-formatted heuristic money rejected by
  validation, a deprecated `DISTINCT ON` form, a duplicate-detection expectation
  that was wrong in the corpus, and a batch upload whose duplicate rollback
  discarded files accepted earlier in the same request.

### Honest limitations

- Correctness is established by tests and measured behaviour, not by a
  line-by-line human audit of every generated line.
- The evaluation corpus is **synthetic** (generated by
  `scripts/make_eval_dataset.py`), so the reported accuracy is an upper bound for
  clean, well-formed invoices, not a field estimate for arbitrary real scans.
- Development-time token/cost accounting was not instrumented; only runtime LLM
  usage is measured (see the metrics report).

## 2. Runtime AI in the product

| Purpose | Provider / model | Where |
|---|---|---|
| OCR for scans and images | OpenParser, `paddleocr-vl-1.6` (PaddleOCR-VL) | `app_core/clients/openparser.py` |
| Field extraction | NVIDIA NIM, `openai/gpt-oss-20b` | `app_core/clients/llm.py`, `app/llm/extract.py` |
| Chunk/query embeddings | NVIDIA NIM, `nvidia/nemotron-3.5-embed-1b` (2048 native, requested at 1536) | `app_core/clients/embeddings.py` |

OCR is invoked only for images and scanned PDFs; digital PDFs use `pdfplumber`
and spreadsheets use `pandas`, so no AI call is made for machine-readable text.
TIFF is out of scope for v1.

Embeddings are called with no prompt: the same text that is already stored in
`text_chunks` is sent as `input_type="passage"` by the worker's `index` stage, and
the user's query is sent as `input_type="query"` by `GET /search?semantic=true`
(the model is asymmetric, so the two input types must differ). Searches fuse the
vector result list with the keyword list by reciprocal rank fusion.

### 2.1 OCR request

The only OCR parameter we choose is the model:

```python
client.parse.sync({"ocr_model": "paddleocr-vl-1.6"}, file=path)
```

Page text and per-page confidence come back normalized to
`{"pages": [{"page_number", "text", "confidence"}]}`. No prompt is sent — OCR is
a document-to-text conversion, not a generation task.

### 2.2 Extraction prompts (verbatim)

Called with `temperature=0.0` and `max_tokens=2000`, expecting a JSON object.

**System prompt**

```text
You are an invoice-data extraction engine. Extract fields from the document text into EXACTLY this JSON shape (no extra keys, no commentary):
{"invoice_number": {"value": str|null, "confidence": 0.0-1.0}, "invoice_date": {"value": "YYYY-MM-DD"|null, "confidence": 0.0-1.0}, "supplier_name": {"value": str|null, "confidence": 0.0-1.0}, "customer_name": {"value": str|null, "confidence": 0.0-1.0}, "subtotal": {"value": number|null, "confidence": 0.0-1.0}, "tax": {"value": number|null, "confidence": 0.0-1.0}, "total": {"value": number|null, "confidence": 0.0-1.0}, "currency": {"value": str|null, "confidence": 0.0-1.0}, "line_items": [{"description": str|null, "quantity": number|null, "unit_price": number|null, "amount": number|null, "confidence": 0.0-1.0}]}
RULES: Use ONLY what appears in the text. If a value is absent or unreadable, use null with confidence 0. NEVER guess or invent values. Numbers are plain floats without currency symbols or thousands separators. Line items are the rows describing goods/services (description, quantity, unit price, amount) — extract every such row you find, even when the input is flat 'label: value' text rather than a table.
```

(The literal newlines in the source are preserved above; the code builds the same
string as adjacent Python literals.)

**User prompt**

```text
Spreadsheet columns: ["Invoice Number", "Invoice Date", ...]   # spreadsheets only

Document text:
<first 12,000 characters of the parsed text>
```

The spreadsheet-columns line is omitted for PDFs and images.

**Repair retry.** If the response is not valid JSON or violates the schema, one
retry is issued with the same system prompt and this suffix appended to the user
message:

```text
Your previous answer was not valid per the schema. Return ONLY the JSON object.
```

If the retry also fails, the LLM pass yields an empty result and extraction falls
back to heuristics alone — the document is still processed.

### 2.3 Guardrails against hallucination

- **Heuristics run first and win.** Regex matches are boxed evidence with the
  matched span; an LLM value never overrides a matched value.
- **Absent means absent.** Missing fields are stored as `null` with confidence
  `0.0`; `document_confidence` is the mean over populated fields only.
- **Schema-enforced output.** `ExtractionOut` validates types, the ISO date form
  and nullability; invalid output is retried once, then discarded.
- **Post-hoc checks are non-AI.** The six validation rules, duplicate detection
  (supplier + invoice-number equality against stored extractions) and search
  ranking are deterministic code; no model decides whether a document passes.
- **No autonomy.** The model cannot call tools, write to the database or trigger
  reprocessing; it only returns fields for one document.

### 2.4 Measured behaviour

From `docs/metrics_report.md` (31 documents, real providers):

| Metric | Value |
|---|---|
| Macro field accuracy | 0.9957 |
| Hallucinated values for absent fields | 0.0 (2 absent-field cases) |
| Line-item precision / recall | 1.0 / 1.0 |

## 3. Reproducing these claims

```bash
# tests (needs TEST_DATABASE_URL — a dedicated dev project)
for p in packages/app-core services/processing services/api; do (cd $p && uv run pytest); done

# evaluation with real OCR + LLM
uv run --project services/processing python scripts/make_eval_dataset.py
uv run --project services/processing python scripts/evaluate.py --workers 4
```

`docs/metrics.json` contains the per-document inputs and outputs behind every
number in the report.
